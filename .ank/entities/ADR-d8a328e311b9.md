## Context

A verifier is a named command declared under `verifiers.<name>` in
`config.yml`, run by `ank done` through `sh -c` (SPEC-77d99d8d1ef2). Its definition is
hashed (`run` and `timeout`, `verify::definition_hash`), and every proof entry
records `verifier: <name>@<hash>`. The definition says what runs, not where.
Today the environment is implicitly the machine of whoever runs `done`.

Two upcoming uses need more than that:

- **Replay.** An independent executor must be able to run the verifier in an
  environment that does not depend on the agent's machine.
- **Reuse.** A result may only stand in for an execution if everything that can
  change it is part of its identity.

If the environment were declared outside the verifier definition (for instance
in an executor's own configuration), the proof hash would not cover it.
Swapping the environment would then weaken a verifier without any proof or
`check` noticing, which is the exact window the definition hash was introduced
to close.

## Decision

1. A verifier definition may carry an optional `env` block:
   - `image`: an OCI image pinned by digest (`sha256:`). Tags are refused at
     parse time.
   - `platform`: `os/arch`. Required when `image` is present.
   - `vars`: environment variables with fixed values. No variable from the
     caller's environment is passed through.
   - `network`: `none` or `open`. Defaults to `none` when `image` is present.
2. A verifier definition may carry optional `inputs`: globs relative to the
   repository root.
3. The definition hash covers `env` and `inputs`. No new proof field is needed
   for the environment: `name@hash` already pins it. Changing the environment
   is a verifier change and is reported as one.
4. **Hermeticity is derived, never declared.** A verifier is hermetic if and
   only if `image` is pinned and `network` is `none`. There is no `hermetic`
   field, for the same reason `blocked` is derived: a declared property is one
   an agent can get wrong. A verifier with a pinned image and `network: open`
   can be replayed but is not hermetic.
5. `ank` runs verifiers as it does today, on the host, and does not require a
   container runtime. A local proof records that the definition `name@hash` was
   run. It does not claim the run happened inside `env`, and `done` emits no
   signal about it. Running inside the declared environment is the job of an
   independent executor, whose result is a detached attestation under its
   process identity.
6. `inputs` are part of the definition hash and of any result identity. An
   executor that reuses results must expose only the declared inputs to the
   verifier, so that an undeclared dependency fails instead of producing a
   false hit. An executor that only replays is not bound by this. Without
   `inputs`, the whole tree is the input.
7. When the declared environment cannot be obtained (image unavailable,
   platform unsupported), the executor exits 9 (verification environment
   failure), never 1. This is not a task failure.

## Example

```yaml
verifiers:
  auth-tests:
    run: cargo test -p auth
    timeout: 10m
    env:
      image: ghcr.io/example/rust@sha256:<digest>
      platform: linux/amd64
      vars: { RUSTFLAGS: "-D warnings" }
      network: none
    inputs:
      - "crates/auth/**"
      - "Cargo.toml"
      - "Cargo.lock"
```

## Consequences

- Existing verifiers are unchanged and remain valid. They are not hermetic:
  they can be replayed on a matching host, but no executor may reuse their
  results.
- Adding `env` or `inputs` to an existing verifier changes its definition hash,
  so existing proofs refer to the old definition. `check` reports it as it does
  for any verifier change.
- The new fields are written through `ank config`, as every key of
  `config.yml` is (ADR-e64dfaafd578).
- SPEC-77d99d8d1ef2 describes the definition hash as covering `run` and `timeout`; it
  is amended to name `env` and `inputs` when this is implemented.
- Whether and how an executor reuses results across machines is not specified
  here.

## Rejected alternatives

- Environment in an executor's configuration: not covered by the proof hash,
  reopens post-hoc weakening.
- A declared `hermetic: true`: self-declaration of a property that matters for
  trust.
- Image tags: mutable, same name for different environments.
- Nix or a specific build system as the environment format: too heavy to
  require. A discriminator inside `env` can be added later if a second format
  is justified.
- `ank` running verifiers in containers locally: adds a runtime dependency to a
  tool with nothing to run.
